Experimental local build

Source was extracted from upstream Thanos-Wrapper source.zip.
The current build reaches menus and displays a 3D scene in DOOM: The Dark Ages
on GTX 1080 Ti / NVIDIA 582.28. The user confirmed normal operation on 2026-11-03.
A later gameplay session ended in a confirmed GPU device-loss hang after about
30 minutes. A repeat failure after approximately two hours on 2026-11-05
reported an invalid GPU memory write. The robustness candidate below failed to
prevent a repeat after 13 minutes. Checkpoints and 30 FPS pacing subsequently
recorded another invalid-write fault after almost four hours. Sustained stability,
FSR and other GPUs remain unverified; indirect-buffer checks are experimental.

Build on Windows with PowerShell, llvm-mingw x86_64 and Vulkan-Headers:

  .\build.ps1 -Toolchain C:\path\to\llvm-mingw -VulkanHeaders C:\path\to\Vulkan-Headers -BuildProbe

Tested compiler: llvm-mingw 20261020 UCRT x86_64.
Tested headers: Vulkan-Headers 1.4.335.
Output: build\vulkan-1.dll and build\probe.exe. Generated binaries are ignored by Git.
The GNU assembly export thunks are generated from exports_cpp.inc.
Existing Visual Studio project and MASM files are retained.

GPU / dispatch probe:

  .\build\probe.exe

This uses the system Vulkan loader and prints native capabilities. It creates a
device, queries a one-triangle acceleration structure size, and submits a small
timestamp command buffer if the selected queue supports timestamps. The fence
wait is bounded at five seconds. Exit 77 means no suitable GPU was tested.

Wrapper probe:

  Copy-Item "$env:WINDIR\System32\vulkan-1.dll" .\build\vulkan-1_real.dll
  .\build\probe.exe "$PWD\build\vulkan-1.dll"

The probe verifies recursive resolver identity, agreement between advertised
rayQuery features and extensions, and a real AS size query through the proxy.
It does not validate game shaders, rendering, ray queries or Float16 emulation.

Runtime diagnostics regression test:

  .\build.ps1 -Toolchain C:\path\to\llvm-mingw -VulkanHeaders C:\path\to\Vulkan-Headers -BuildTests
  .\build\runtime_diagnostics_test.exe

Run once with RuntimeTrace=0 (or no INI) and once with RuntimeTrace=1 in
build\Thanos-wrapper.ini. It uses synthetic API functions, verifies unchanged
query arguments, output data and native error results, and tests bounded fault
capture with device-handle reuse and CPU backoff after device loss. It does not
force a real GPU fault.

RuntimeTrace=1 in the [diagnostics] section enables runtime error/heartbeat logs
and native VK_EXT_device_fault reporting when supported. It does not recover
a lost device, change query results or automatically terminate the application.
Query polling yields for 10 ms only after a native VK_ERROR_DEVICE_LOST result,
regardless of RuntimeTrace. Normal VK_NOT_READY polling is unchanged.

Memory robustness candidate (off by default):

Add RobustAccess=1 under [experiments] in build\Thanos-wrapper.ini. Only
driver-supported guards are enabled; [ROBUST] logs the selected feature bits.
The game-tested preset also enables PascalRTGate=1 and RuntimeTrace=1.
This candidate is not included in the v0.1.0-pascal.1 release archive.

With -BuildTests, the build also produces robust_access_test.exe (feature-chain
policy tests) and robust_gpu_test.exe (real compute dispatch through the wrapper).
Compile the original test shader with glslangValidator and validate its SPIR-V:

  glslangValidator -V --target-env vulkan1.2 tests\robust.comp -o build\robust.spv
  spirv-val --target-env vulkan1.2 build\robust.spv
  .\build\robust_access_test.exe
  .\build\robust_gpu_test.exe "$PWD\build\vulkan-1.dll" "$PWD\build\robust.spv"
  .\build\robust_gpu_test.exe "$PWD\build\vulkan-1.dll" "$PWD\build\robust.spv" features2

The GPU test requires the current wrapper, a sibling vulkan-1_real.dll,
RobustAccess=1 and native nullDescriptor/robustBufferAccess2 support. Exit 77
means skipped. It verifies null reads return zero, null and out-of-range stores
are discarded, a valid write completes and other buffer data is preserved.
It does not exercise the game shaders, image robustness or buffer-device-address
accesses, nor establish sustained gameplay stability.

GPU checkpoints and frame pacing (off by default):

  [experiments]
  PascalRTGate=1
  RobustAccess=1
  FrameLimit=30
  [diagnostics]
  RuntimeTrace=1
  GpuCheckpoints=1
  ShaderDumpDirectory=

FrameLimit accepts 10-240 FPS and delays presentations per queue on the host;
zero/invalid values disable it. GpuCheckpoints requires RuntimeTrace=1 and native
VK_NV_device_diagnostic_checkpoints support. [CHECKPOINT] confirms enablement and
the first instrumented command. [CHECKPOINT-FAULT] is emitted after native device
loss, with bounded history and explicit reporting of expired/external tokens.
These options are a diagnostic/load-reduction experiment, not a proven fix.

  .\build\checkpoints_test.exe

Build this test with -BuildTests. Use the above INI; it runs synthetic API calls,
checks marker ordering, arguments, pipeline identity, bounded history/reporting,
lifetime cleanup and pacing. It does not cause a real GPU fault. The real GPU
test above can also run with GpuCheckpoints=1; it exercises checkpoint insertion
while reading back a compute result, without querying a healthy device's fault
checkpoints. See docs/TECHNICAL.md for coverage and limitations.

Indirect-count bounds guard (off by default):

Add IndirectBounds=1 under [experiments]. Buffer sizes are tracked when this guard
or GpuCheckpoints is requested. The guard caps maximum count to known buffer
capacity and skips known invalid offset/count ranges or stride. Unknown handles
are forwarded unchanged. It does not validate GPU-written counts or index data,
synchronization, descriptors or physical buffer addresses. First 32 adjustments
are logged; checkpoint fault records include the original and forwarded values.
No invalid game draw arguments have yet been established from the captured fault.

  .\build\indirect_bounds_test.exe

Run with IndirectBounds=1 and again with IndirectBounds=0, keeping GpuCheckpoints=1
to verify tracking without mutation. The test covers unsigned overflow, sizes,
alignment/stride, unknown resources, argument forwarding and handle lifetime.

Compile and validate the original rendering test shaders:

  glslangValidator -V --target-env vulkan1.2 tests\indirect.vert -o build\indirect.vert.spv
  glslangValidator -V --target-env vulkan1.2 tests\indirect.frag -o build\indirect.frag.spv
  spirv-val --target-env vulkan1.2 build\indirect.vert.spv
  spirv-val --target-env vulkan1.2 build\indirect.frag.spv
  .\build\indirect_gpu_test.exe "$PWD\build\vulkan-1.dll" "$PWD\build\indirect.vert.spv" "$PWD\build\indirect.frag.spv"
  .\build\indirect_gpu_test.exe "$PWD\build\vulkan-1.dll" "$PWD\build\indirect.vert.spv" "$PWD\build\indirect.frag.spv" gipa

This test requires the current wrapper with IndirectBounds=1, its sibling native
loader, Vulkan 1.3 dynamic rendering and indirect-count support. A 20-byte argument
buffer holds one indexed command; the wrapper must reduce maximum count 2 to 1.
The GPU draws a triangle into a 4x4 image, waits at most five seconds and checks
all 16 pixels. Test both with checkpoints enabled and disabled. Passing this
small rendering test does not establish a fix for the observed gameplay fault.

Changes in this branch:
- Preserve wrapper resolvers and extension enumeration when obtained through GIPA.
- Preserve the wrapper GDPA when it is requested through itself.
- Keep copied pNext nodes at stable addresses.
- Preserve Vulkan 1.3 and the NV feature nodes requested by the tested game.
- Enable the driver's supported native AS / RT pipeline feature subset.
- Support building with llvm-mingw and report proc requests without logging an
  unresolved placeholder as though it were the final resolution result.

The upstream feature spoofing and other unfinished compatibility
code remain experimental. This is not a complete Vulkan implementation.

Pascal RT initialization experiment (off by default):

Place Thanos-wrapper.ini next to the wrapper DLL:
  [experiments]
  PascalRTGate=1
  [diagnostics]
  ShaderDumpDirectory=C:\existing\diagnostic-directory

The experiment exposes the NV_mesh_shader extension name without changing native
mesh feature bits. It isolates DOOM's NVIDIA-specific RT function-loader gate;
it does not implement mesh shaders or claim Vulkan conformance. Unsupported
extension names are filtered out before calling the driver's vkCreateDevice.
No game binary patch or game-console command is used.

ShaderDumpDirectory must already exist. Omit it to disable binary captures.
Captures are deduplicated and capped at 256 MiB per process. Keep proprietary
game shaders and crash dumps outside this repository. The environment variables
THANOS_PASCAL_RT_GATE and THANOS_SHADER_DUMP_DIR override the corresponding INI
options. They affect the wrapper only.

Observed in development run 5: menu displayed, 1051 shader modules captured;
673 use 16-bit floating types, 110 declare RayQueryKHR, none declare MeshShadingNV.
These counts do not prove successful execution of every shader. Native Float16
and rayQuery feature queries still report unsupported; there is no lowering
implementation in this branch.

Native RT rendering correction (development run 6):
- Forward direct/indirect vkCmdTraceRays calls to the driver's real entry points.
- Remove automatic RT output debug clears from the dispatch path.
- Keep ShadowLift disabled unless explicitly enabled and never submit it while
  acquiring a swapchain image, before acquisition synchronization has completed.
- Record native RT pipeline creation results; allow reading logs while running.

The menu-only build still swallowed ray dispatches. The user reported no 3D
image and a black screen after changing FSR and another graphics setting. The
captured FSR3 shaders are FP32, so attributing that issue to FP16 is unsupported.
